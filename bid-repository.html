A searchable bid file repository

Five years of freight bid files sat in 55 GB of spreadsheets nobody could search. The sales team was quoting new business blind.

The problem

Every customer bid arrives as its own workbook. Different customer, different template, different column names, different number of header rows before the data starts. Once a bid is won or lost the file goes into a folder and is effectively gone.

That is fine until a rep is on a call and wants to know whether the company has ever run a lane before — and at what volume. Answering meant opening files one at a time and hoping. In practice it meant guessing.

55 GB is roughly 11 million printed pages. The data existed. It just wasn’t reachable.

How I worked it

  1. ScopeTalked to reps about the questions they actually needed answered on a call.
  2. BrainstormMapped what a usable answer looks like: lane, customer, volume, miles, year.
  3. SolutionsChose a parse-and-normalize pipeline over asking anyone to change how they file bids.
  4. Data cleanupHeader detection, column mapping, deduplication across inconsistent templates.
  5. ReportBuilt the Power BI model and the three views reps would use.
  6. TestingSat with reps, watched them fail to find things, fixed the views.
  7. PresentingWalked leadership through it as my end-of-internship capstone.
  8. HandoffDocumented the pipeline so new bid files could be folded in after I left.

The order matters here — steps four and six are where the project was actually won or lost.

The hard part

Not the dashboard. The parsing. No two bid templates agreed on what to call an origin city, and the header row was rarely the first row — most files open with a title block, a logo, and a blank line. A script that assumes header=0 silently produces garbage across thousands of sheets.

So the pipeline scans the first ten rows of every sheet, scores each one for how many recognizable column spellings it contains, and treats the best-scoring row as the header. Column spellings live in a lookup table rather than in the logic, which is what let the thing survive contact with bid formats it had never seen. Sheets that can’t be matched are reported rather than silently dropped — a quiet failure in a consolidation script is worse than a loud one.

The core of the parser, which is the piece the whole project rested on:

# Canonical field -> the header spellings seen in the wild.
SCHEMA = {
    "origin_city":  ["origin city", "org city", "city (origin)"],
    "origin_state": ["origin state", "org state", "origin st"],
    "origin_zip":   ["origin zip", "org zip", "origin postal code"],
    "dest_city":    ["destination city", "dest city", "dst city"],
    "dest_state":   ["dest state", "destination_state", "dst state"],
    "dest_zip":     ["dest zip", "destination_zip", "dst zip"],
}


def find_header_row(frame):
    """Return the index of the row that looks most like a header, or None.

    A row qualifies when it contains recognizable spellings for at least
    half the canonical fields. Scanning beats assuming header=0: these
    workbooks routinely open with a title, a logo row, and a blank line.
    """
    best_index, best_score = None, 0
    for i in range(min(10, len(frame))):
        cells = {str(v).strip().lower() for v in frame.iloc[i].values}
        score = sum(1 for spellings in SCHEMA.values()
                    if cells & set(spellings))
        if score > best_score:
            best_index, best_score = i, score
    return best_index if best_score >= len(SCHEMA) / 2 else None


def extract_sheet(frame):
    """Project one sheet onto the canonical schema, filling absent fields."""
    lookup = {str(c).strip().lower(): c for c in frame.columns}
    out = pd.DataFrame(index=frame.index)
    for field, spellings in SCHEMA.items():
        match = next((lookup[s] for s in spellings if s in lookup), None)
        out[field] = frame[match] if match else pd.NA
    return out

Python 3 with pandas. The full script walks a directory, tags every row with its source file and sheet, and reports unmatched sheets on stderr rather than dropping them silently.

Why three views and not one

The first version was a single table with every field and a pile of slicers, which tested badly — people could not find the thing they came for. Splitting it by question rather than by data structure is the change that made it get used.

The second piece

Once bid history was queryable, the same pattern extended forward: incoming carrier bids now file themselves into a report that pricing and senior leadership use for carrier selection.

Bid template→Email to carriers→Power Query→Normalize→Award→Repository

The template is the leverage: standardizing what comes back is cheaper than parsing whatever arrives.

What I took from it

Two things. First, the value was in the cleanup, not the visualization — the dashboard was a week and the parsing was the rest of the summer, and only one of those was the actual problem. Second, a tool nobody can navigate is a tool nobody uses, and you find that out by watching someone try, not by asking them if it looks good.
